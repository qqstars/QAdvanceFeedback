# QAdvanceFeedback

[English](README.md) · **简体中文**

一个 SimHub 插件，把车轮抱死与车轮打滑转换成 **0-100 的统一刻度**——这个刻度在任何车型下含义都相同，另外还提供 8 个 G 力通道，用于座椅震动垫的体感提示。面向 ShakeIt Bass Shakers 与 ShakeIt Motors 设计。

---

## 为什么需要这个插件

原始的纵向车轮打滑率有一个物理上的问题，无论怎么调整量程都解决不了：**越过轮胎抓地力曲线的峰值之后，系统不存在平衡点。** 峰值以下，打滑越多、制动（或驱动）力越大，车轮会自行稳定下来；峰值以上，打滑越多、力反而**越小**，于是打滑进一步加剧——车轮就此失控，大约 **100-300 毫秒**内完全抱死（或完全打滑）。所以原始信号会一直停留在 0.1-0.2 附近，告诉你一切正常，然后毫无过渡地直接跳到「完全抱死」。等它动的时候，已经来不及反应了。

SimHub 自带的 ShakeIt 插件中已经内置了一个传统 iRacing 车轮抱死/打滑效果（`WheelSlipEffect`），它精确复现了上述这道悬崖——这是一个成熟可靠的算法，但它是**未归一化**的：输出的量程会随车型、路面和条件而变化，所以「0.4」这个读数在 GT 赛车里和敞轮方程式赛车里的含义完全不同。没有办法把它直接绑定到震动器上，并在你的整个车库里获得一致的体感。

**本插件精确复现了 SimHub 自身的传统 iRacing 算法**（下面的第 3 层——同样基于转速/车速推导出的抱死与打滑计算，已通过对 SimHub 自身反编译代码的比对验证）**，然后再对其进行归一化和整形**，转换成一个 0-100 的信号，其区间在任何车上含义都相同：**0-30 表示轻微、仍有余量；30-60 是理想工作区间——你的最佳表现区，应保持在这里；60-80 表示轮胎正开始抱死（或打滑）——尚未完全发生，但已非常接近，请立即减轻刹车/油门；100 表示完全抱死或完全打滑**——无论你开的是什么车，含义始终一致。在此基础上，插件还额外提供了 8 个 G 力通道，让座椅震动垫可以直接体现刹车、加速和过弯载荷，与车轮通道彼此独立。

### 有没有考虑过直接读取 ShakeIt 自身的内部数值？

只针对纯内部效果状态——是的，并且已通过反编译验证这条路走不通：`ShakeITBSV3Plugin` 和 `ShakeITMotorsV3Plugin` 本身都没有把这部分内部状态单独暴露为 SimHub 属性。**不过 SimHub 的 ShakeIt Motors 特效确实提供了一个显式的、可选启用的「将输出值导出为属性」选项**（见下文「使用 ShakeIt Motors 作为数据源」）——这是本文档早前的一个错误结论，在真正反编译并确认导出路径可行之后已经更正。第 4 层（「Normalized」，见下文）仍然默认使用自己的 `Raw.*` 属性作为出厂默认输入源，因为导出属性的确切名称取决于你启用的是哪个 ShakeIt 插件变体，以及你在其「Property name」字段中输入的内容——本插件无法安全地为此猜测一个固定默认值。

## 五层架构

遥测数据依次经过五层，每一层都独立发布，你可以根据自己的装备绑定最合适的那一层：

| 层 | 发布前缀 | 内容 |
|---|---|---|
| 1 | （内部） | 与游戏无关的遥测接口——每款游戏自己的读取器都会归一化成这个形状。 |
| 2 | （内部） | SimHub 遥测适配器——把真实的 `GameData` 帧读入第 1 层的形状。 |
| 3 —— **Raw（原始值）** | `WheelLock.Raw.*` / `WheelSlip.Raw.*` | SimHub 自身的传统 iRacing 转速/车速算法，精确复现，按车轮分别缩放到 0-100 并截断。`Front`/`Rear`/`Left`/`Right`/`All` 随后由这四个逐轮数值通过一套可配置的、具有物理依据的载荷转移方案组合而成（见下文「车轮组合」）——Normalized/Projected 继承的是同一套方案（各自对自己的逐轮输出重新计算，而不是直接复用 Raw 自己的聚合数值）。按设计未归一化——这是忠实复现，而不是修正。其刹车/油门踏板阈值均可配置（见下文「踏板阈值」）——这是刻意偏离 SimHub 自身硬编码数值的设计。 |
| 4 —— **Normalized（归一化值）** | `WheelLock.Normalized.*` / `WheelSlip.Normalized.*` | 把 Raw 的逐轮*形状*，与仅通过车速/油门/刹车/G 力（不使用逐轮打滑数据，不依赖任何第三方插件）学习到的、相对于本车的严重程度结合起来——这正是让区间在一辆经常拉 4G 的街机风格赛车和一辆经常拉 1.2G 的模拟风格赛车中含义相同的关键。（之所以叫这个名字，是因为这一层实际做的事情就是：针对本车已学习到的峰值进行归一化——而不是在宣称「可靠」。） |
| 5 —— **Projected（映射值）** | `WheelLock.Projected.*` / `WheelSlip.Projected.*` | 把 Normalized 的输出送入你自己可编辑的曲线（起始/轻微/理想/严重/结束锚点），并可选地在达到最大值时改为脉冲振动，而不是持续保持。**请绑定这一层**，以获得经过整形、可调节的体感。（命名来自曲线编辑器自身的「输出映射（output projector）」机制。） |

> **已从「Reliable」/「Final」更名为「Normalized」/「Projected」**（本插件尚未上线或在真实 SimHub 会话中被绑定过，因此这次更名不会对任何现有安装造成破坏——但如果你已经把旧属性名手动输入到某个 ShakeIt 自定义效果里，**需要重新绑定为上面的新名称**）。

每一层都发布相同的九个逐轮/分组目标：`FrontLeft`、`FrontRight`、`RearLeft`、`RearRight`、`Front`、`Rear`、`Left`、`Right`、`All`——9 个目标 × 3 层 × 2 个通道（抱死、打滑）= **54 个属性**，始终发布。

### G 力通道（8 个属性，始终发布）

与车轮通道相互独立——参考了经典的洗出（washout）/运动感知算法建模（见下文「参考资料与版权说明」），把你正保持的稳定强度与达到该强度过程中的动态变化区分开来：

```
QAdvanceFeedback.GForce.Bottom.FrontLeft   .FrontRight   .RearLeft   .RearRight
QAdvanceFeedback.GForce.Back.LowLeft       .LowRight     .TopLeft    .TopRight
```

## 如何在 SimHub 中使用

### 安装

1. 把 **`QAdvanceFeedback.dll`** 复制到你的 SimHub 目录（包含 `SimHubWPF.exe` 的那个目录）。
2. 启动 SimHub，在提示时批准该插件。
3. 在插件列表中启用它。

只有一个文件，无需复制任何其他内容，也没有依赖项需要安装。

### 在 ShakeIt Bass Shakers / ShakeIt Motors 中绑定

**SimHub 内置的 ShakeIt 效果无法读取插件属性。** 你必须添加一个**自定义效果（Custom effect）**——这是 ShakeIt Bass Shakers 和 ShakeIt Motors 中唯一能够按名称绑定任意属性的效果类型。

在任一 ShakeIt 编辑器中：添加一个**自定义效果**，然后将其指向你想要的属性，例如 `QAdvanceFeedback.WheelLock.Projected.All` 或 `QAdvanceFeedback.WheelSlip.Projected.FrontLeft`。

**这些属性都采用 0-100 的刻度。** 请将自定义效果配置为该量程——如果它期望的是 0-1，那么所有超过 1 的数值都会饱和，一踩刹车震动器就会立刻处于满强度。

### 按装备类型推荐的绑定方式

| 装备 | 属性 |
|---|---|
| 单个低音震动器/座椅 | `QAdvanceFeedback.WheelLock.Projected.All` 和/或 `QAdvanceFeedback.WheelSlip.Projected.All` |
| 四个角落电机 | `QAdvanceFeedback.WheelLock.Projected.FrontLeft` / `.FrontRight` / `.RearLeft` / `.RearRight` |
| 双通道，前/后 | `QAdvanceFeedback.WheelLock.Projected.Front` / `.Rear` |
| 双通道，左/右 | `QAdvanceFeedback.WheelLock.Projected.Left` / `.Right` |

车轮打滑通道的绑定方式相同，使用各自独立的自定义效果，绑定到 `QAdvanceFeedback.WheelSlip.Projected.*` 下——这样两个通道就可以独立调节到不同的电机上，或者共用同一批电机。

### 数据来源：ShakeIt 插件输出属性（默认）与手动模式

车轮抱死/车轮打滑每个通道的四个车轮**数据源**（第 4 层的输入，不要与上文第 5 层的绑定混淆）标签页最顶部都有一个切换开关：**「ShakeIt 插件输出属性」**（出厂默认，两个通道均如此）与**「手动」**（本插件自身的 `Raw.*` 属性，或你自己填写的任意内容）。该开关**始终可见、始终可切换**，无论 SimHub 当前是否已报告 ShakeIt 导出的属性——如果尚未报告，标签页会显示一条提示，并给出下方的设置步骤，而不是把这个选项隐藏起来。

选择 ShakeIt 模式后，四个车轮的数值会直接读取 SimHub 自身的 ShakeIt Motors「Wheels lock」/「Wheels slip」特效：

1. 启用 **ShakeIt Motors** 插件（SimHub 设置 → 附加插件），并创建一个配置文件。
2. 添加一个 **Wheels lock** 特效（车轮抱死标签页）/ **Wheels slip** 特效（车轮打滑标签页）——分组为「Slip and lock」。
3. 勾选 **「Use legacy IRacing algorythm」**（SimHub 自身的拼写），使其与本插件自身的第 3 层算法保持一致。
4. 勾选 **「Export output value as a property」**，并将 **「Property name」** 设置为准确的 `WheelLock.IRacing`（车轮抱死）或 `WheelSlip.IRacing`（车轮打滑）——本插件的这个开关正是期望这些确切的名称，已根据 SimHub 自身反编译出的命名规则（`<插件类型>.Export.<属性名>.<位置>`）确认：
   ```
   ShakeITMotorsV3Plugin.Export.WheelLock.IRacing.FrontLeft   .FrontRight   .RearLeft   .RearRight
   ShakeITMotorsV3Plugin.Export.WheelSlip.IRacing.FrontLeft   .FrontRight   .RearLeft   .RearRight
   ```
5. 在同一个特效的输出行上勾选 **「Disable output」**，使其不驱动任何硬件——它仍会持续计算并导出该属性。

在 SimHub 报告某个通道的全部四个车轮属性之前，该通道会自动回退到自身的 `Raw.*` 数值（绝不会把缺失的属性当作 0 读取），所以在你完成上述设置之前，该通道不会失去输出。

选择**手动**模式时，上述设置步骤会被隐藏，取而代之的是一条简短提示：每个车轮的数据源字段必须自行提供一个 0-100 的数值（0 = 未抱死/未打滑，100 = 完全抱死/完全打滑）。每个通道下方的**恢复默认值**按钮，会始终恢复到**当前所选**的模式——ShakeIt 模式下恢复上述四个 ShakeIt 属性名，手动模式下恢复本插件自身的 `Raw.*` 属性名——它不会把你切换到另一个模式。

完整的、经过反编译验证的操作步骤（包括 SimHub 界面上的确切文字）：`docs/shakeit-export-guide.md`。

### 踏板阈值（可自行配置，刻意偏离 SimHub 自身的硬编码数值）

车轮抱死和车轮打滑都会在底层算法生效之前先检查踏板位置——这在手动模式和 ShakeIt 模式下均适用，因为它作用于第 3 层本身：

| 设置项 | 默认值 | 作用 |
|---|---|---|
| 车轮抱死——刹车阈值 | **20%** | 只有当刹车踏板超过此百分比时，才会认为车轮正在抱死。 |
| 车轮打滑——刹车阈值 | **100%** | *优先*检查——一旦超过，打滑数值将与抱死使用相同的刹车数值（这与 SimHub 自身未区分抱死/打滑的原始算法保持一致）。默认设为 100% 是刻意为之：踏板本身不可能超过 100%，因此该分支默认永远不会生效，打滑将只由油门触发，这正是预期行为。 |
| 车轮打滑——油门阈值 | **40%** | 仅当上述刹车阈值未被触发时才会检查。同时要求离合器踏板低于 5%（这是 SimHub 自身固定的规则，不可配置）。 |

### 8 通道座椅震动垫（G 力）

`GForce.Bottom.*` / `GForce.Back.*` 这 8 个属性可以直接映射到一套 8 垫座椅/靠背装备上，布局为坐垫（前/后 × 左/右）和靠背（下/上 × 左/右）：

| 震动垫 | 属性 | 什么情况下会触发 |
|---|---|---|
| 坐垫，左前 | `QAdvanceFeedback.GForce.Bottom.FrontLeft` | 重刹车（坐垫前部，刹车时体重前移的位置） |
| 坐垫，右前 | `QAdvanceFeedback.GForce.Bottom.FrontRight` | 重刹车 |
| 坐垫，左后 | `QAdvanceFeedback.GForce.Bottom.RearLeft` | 共享区域：中等刹车和中等加速都会经过这里 |
| 坐垫，右后 | `QAdvanceFeedback.GForce.Bottom.RearRight` | 共享区域 |
| 靠背，左下 | `QAdvanceFeedback.GForce.Back.LowLeft` | 共享区域：刹车的起始点和加速的中间点 |
| 靠背，右下 | `QAdvanceFeedback.GForce.Back.LowRight` | 共享区域 |
| 靠背，左上 | `QAdvanceFeedback.GForce.Back.TopLeft` | 持续的重加速（被推向靠背顶部） |
| 靠背，右上 | `QAdvanceFeedback.GForce.Back.TopRight` | 持续的重加速 |

左右两侧会根据侧向 G 力产生偏置（方向切换见下方「常规」一节）——过弯时负荷较大的一侧读数最高可达无偏置时的 1.5 倍，负荷较小的一侧可低至 0.5 倍。

**建议的赫兹范围及频率映射原理：** 每个震动垫的*数值*（0-100）用于驱动你的震动器/震动垫控制器的振幅，而其*频率*则在你的 ShakeIt 通道配置中一次性设置好，遵循的约定是**数值接近 0 时使用高频（细腻），数值为 100 时使用低频（有力）**。G 力设置标签页会实时显示建议值（默认**数值 0 对应 100 赫兹，数值 100 对应 50 赫兹**——根据实际上手体验先后调整过两次：最初的 300 赫兹在数值区间低端手感过于生硬单薄，随后改用的 20 赫兹低端又力度不足），并限制在声明的设备能力范围 **10-300 赫兹**之内。请将每个 ShakeIt 通道自身的「起始赫兹」/「结束赫兹」字段配置为与设置页面中显示的建议值一致（如果你更改设备范围，建议值会随之更新）——本插件只发布 0-100 的振幅数值，赫兹映射本身由 ShakeIt 自己的通道配置完成。

## 配置

SimHub 只给每个插件一个设置控件，本插件将其分成四个标签页：**车轮抱死**、**车轮打滑**、**G 力**、**常规**。底部的**应用**按钮会**一次性提交全部四个标签页**的内容，无论当前显示的是哪一个标签页——你不需要逐一点开每个标签页，应用才会生效。应用按钮旁边是**恢复所有默认设置**，它会把每个标签页上的每一项设置——车轮抱死、车轮打滑、G 力、常规——全部恢复为同一个内部定义的默认对象，这样出厂默认值和这个按钮的行为就永远不会互相偏离。由于它会立即覆盖你自己调整过的内容且无法撤销，点击后会先弹出确认对话框。

### 车轮抱死 / 车轮打滑 标签页

每个通道（刹车抱死、油门打滑）都完全自成一体——各自的数据源、各自的曲线、各自的脉冲设置——因此调整其中一个通道永远不会影响另一个。

**数据源。** 每个通道有四个车轮字段（左前/右前、左后/右后）；`All`/`Front`/`Rear`/`Left`/`Right` 始终由这四个字段*聚合*得出（该算法本身没有这些概念）——不能单独*取值*，但具体*如何*聚合现在完全可配置，见紧随其后的「车轮组合」。每个字段默认**直接引用该车轮自身第 3 层的 `Raw` 属性**——这是最简单、最稳健的默认值，完全不需要任何表达式引擎。如果你的 SimHub 安装提供了脚本编辑器/表达式求值器，字段也可以改为填写 SimHub 表达式（JavaScript 或 NCalc）；每个字段旁边的「P」/「J」/「N」小标记会显示当前是哪一种。点击任一标签页上的**恢复默认值**（这是与全局「恢复所有默认设置」不同的独立按钮），可以只把该通道的四个数据源字段恢复为对第 3 层的纯引用，不影响曲线、脉冲或其他标签页。

**影响：** 除非你有特殊理由要让某个车轮从本插件自身计算结果以外的地方取值（例如你希望车轮打滑读取与车轮抱死不同的上游信号），否则不建议改动此处。大多数玩家完全不需要碰这一部分。

**车轮组合（聚合方式）。** 上方四个逐轮数值如何组合成 `Front`/`Rear`/`Left`/`Right`/`All`——这是一套由本插件所有者提供并经过实车验证、具有物理依据的方案，取代了原先那种对载荷转移视而不见的通用平均方案，因为载荷转移正是车轮抱死/打滑提示应当体现的主要真实效应：**刹车时载荷向前转移，前轮承受主要抓地力，因此最为重要；加速时，驱动轮才是打滑的一方。** 该方案包含两个加权求和的混合阶段（都是简单的加权和，因此结果始终连续——不会像单纯「取最大值」那样，在最差车轮发生变化时产生突兀的冲击感）：

- **同轴混合（Front/Rear）：** `Front = Max(FL,FR)×WMax + Min(FL,FR)×WMin`，`Rear` 同理——这两个数值描述的是同一轴上较强车轮与较弱车轮各自的占比。
- **左右/整车混合（Left/Right/All）：** `Left = FL×WFront + RL×WRear`，`Right = FR×WFront + RR×WRear`，`All = Front×WFront + Rear×WRear`——这两个数值描述的是前轴相对于后轴的占比。
- **仅车轮打滑：** 一个下限值，`result = Max(result, Max(参与计算的车轮)×SlipFloorFactor)`，防止单个强烈打滑的车轮被平均掉。车轮抱死默认将其设为 0（禁用）——它自身极端的前轴权重已经能让抱死的车轮强烈地传递出来，并且抱死事件比单轮打滑更常表现为同轴对称；该机制本身是通用的，两个通道都可以使用，只是默认值使其仅对打滑生效。

这五个数值（`WMax`、`WMin`、`WFront`、`WRear`，以及车轮打滑自身的下限系数）均可按通道独立编辑——权重只需保持 ≥ 0（打滑下限系数额外上限为 1）；它们**不会**被强制要求相加等于 1，因此你输入的就是你得到的，绝不会被静默地重新缩放。**出厂默认值——车轮抱死：** `WMax` 0.45，`WMin` 0.55，`WFront` 0.90，`WRear` 0.10，下限不适用。**车轮打滑：** `WMax` 0.55，`WMin` 0.45，`WFront` 0.65，`WRear` 0.35，下限 0.4。

**影响：** 出厂默认值已经体现了「刹车靠前轮承担，打滑靠驱动轴承担」的原则——大多数玩家完全不需要改动这里。如果你的车是前驱（或者你只是希望车轮打滑采用相反的偏向），可以把 `WRear` 调得比 `WFront` 更高（或者把两者完全互换），让你车辆实际的驱动轴在组合读数中占主导。完整推导过程、连续性证明，以及「为什么车轮抱死不需要自己的下限」这一结论，见 `docs/aggregation-report.md`。

**输出整形（曲线）。** 这是最值得花时间调整的部分——它决定了你的震动器拿到这个 0-100 数值之后实际做什么。每一行的含义是「当数值达到这个原始输入值时，发送这个输出值」；两栏都可以独立编辑，因此你既可以调整锚点*位于何处*，也可以调整它*读数有多强*。

| 锚点 | 含义 | 你会感受到什么 |
|---|---|---|
| 起始值 | 低于此值不产生任何输出 | 正常驾驶时保持安静 |
| **轻微**（默认原始值 30，两个通道相同） | 刚刚进入轮胎的工作区间——低于此值仍有余量 | 如果输出值设得低，这是一个温和、容易忽略的提示 |
| **理想**（默认原始值 60，两个通道相同——由「适中」更名而来） | 理想工作区间的边缘——在轮胎开始抱死/打滑之前所能达到的最大有效刹车力度/牵引力 | 你的「甜蜜点」提示——强到能立刻察觉，又温和到可以一圈接一圈地承受 |
| **严重**（默认原始值 80，两个通道相同） | 正处于即将抱死/打滑的边缘——尚未发生，但只差一步 | 一个不容忽视的强烈提示——现在就该松开 |
| 结束值 | 达到或超过此值时，输出始终为最大强度（100） | 情况确实很糟时的满强度反馈 |

两个预设，加上**自定义**（一旦你手动编辑任意一格，会自动切换到这个状态）：

- **线性**——从（起始值，0）到（结束值，100）的一条直线，保留你已设置的起始/结束值而不会覆盖它们。以出厂的起始值 20/结束值 100 为例，即 20→0、60→50、100→100。
- **曲线**（默认）——出厂设定的、经过精心设计的形状。两个通道共用**相同**的锚点原始输入位置（30/60/80/100，已通过数值验证确认「接近极限」落在 75-80 附近、「完全抱死/打滑」正好落在 100——见 `docs/refinements-report.md`）；只有输出强度不同。**车轮抱死：** 起始 20，结束 100，30→10，60→30，80→80。**车轮打滑：** 起始 20，结束 100，30→8，60→20，80→75——整体比抱死曲线更柔和，因为驱动轮的牵引力提示更适合柔和一点出现。

曲线使用单调三次插值进行平滑，因此输出值不会随着输入值上升而*下降*——普通样条曲线可能会出现过冲和回落，你会感觉到震动器恰好在情况变糟的那一刻反而减弱了，这种体验是不可接受的。

**达到最大值时脉冲振动。** 启用后，当某个通道达到 100 时，会在 100 和一个可配置的**最小值**之间来回脉冲，而不是持续保持满强度——如果你希望持续的抱死/打滑比静态嗡鸣更有紧迫感，可以打开它。**间隔（毫秒）**是半个周期（100→最小值 或 最小值→100）；200 毫秒（5 赫兹）的下限由插件本身强制执行，而不仅仅是这个输入框，因此手动修改配置文件也无法绕过它。默认关闭——大多数玩家使用普通的整形输出就已经足够。

### G 力标签页

**最大加速度/刹车 G 值。** 每个轴向（加速、刹车）都可以设置为**固定值**（你自己设定一个 G 值，作为「100%」的基准）或**自动**（插件会在游戏中实际观测到的最大 G 值，按游戏**和**车辆分别学习，并具备离群值剔除机制，因此单次碰撞导致的尖峰绝不会被误认为你的真实峰值——必须有第二次相似的读数出现来确认，才会被采信）。在自动模式下切换游戏或车辆，会自动切换到该组合各自学习到的最大值；彼此之间不会互相影响。默认值：**刹车 2.0G**，**加速 0.9G**——刹车的默认值更高，因为高速时刹车同时受益于轮胎抓地力和空气动力学下压力，而加速则完全受限于牵引力。

**影响：** 如果你的车从未接近 100%，导致震动垫感觉迟钝，可以调低固定值（或改用自动模式）；如果轻微的一脚刹车就已经把仪表打到最大值，可以调高固定值。

**持续感受（持续比例）。** 在持续的重刹车或重加速下，各链条中的后续震动垫会保持*较弱*的振动，而不是完全消失，这样整体感觉会保持连贯，而不是感觉一「移动」到下一个垫子上原来的垫子就突然停了。默认值来自本引擎自身链条结构的推算（每远离已完全饱和的引导垫一跳，比例就减半）：每条链的**中间**垫（刹车链的座垫后部，加速链的靠背下部）默认 **50%**，**最远**的垫（刹车链的靠背下部，加速链的座垫后部）默认 **25%**——形成一个真实的空间梯度，让你能感受到振动*来自哪里*，而不只是感受到它存在。如果你更喜欢原来那种逐渐消失的效果，可以设为 **0%**。

**动态感受（分阶段扫掠）。** 刹车/加速反馈会经过三个阶段传递——先是远端震动垫，再到中间震动垫，最后到最靠近受力方向的震动垫——才会稳定下来，这与你所保持的稳定强度（每个震动垫最终会稳定在什么程度）是分开的。猛踩踏板会带来一次快速而强烈的扫掠；轻柔的变化则带来缓慢而轻微的扫掠。以下三个参数控制这种感觉：

- **强度响应时间**——持续/背景强度跟随实际 G 值变化的速度。数值越大，反应越慢越平滑。
- **扫掠平滑时间**——当输入停止变化后，已锁定的扫掠速率消退的快慢，避免单帧噪声让扫掠突然跳变。数值越大，进入扫掠的过程越柔和渐进。
- **扫掠速度**——同样的 G 值变化下，扫掠本身在震动垫间移动的快慢。数值越大，突然的变化扫掠得越快。

**影响：** 如果你希望整个动画感觉更慢，可以调低扫掠速度（它会让感觉在震动垫间传递得更缓慢），并调高扫掠平滑时间（让它更柔和地渐入，而不是突然跳变）；如果你希望急促的点刹和油门轻点扫掠得更快，可以调高扫掠速度。注意扫掠速度内部设有上限（每秒 5 次扫掠），超过这个值后再调高也不会让扫掠变得更快——而且调高扫掠速度还会降低触发该上限所需的变化速率，超过这一点后，轻柔和剧烈的输入感觉会更相似。默认 **1.2**（相比原先的 1.5 有所降低，车主本人在真实硬件上试用后反馈 1.2 时动画观感更清晰）。

**左右方向。** 侧向 G 力会给左右两侧的震动垫对施加偏置——过弯时负荷较大一侧的读数最高可达无偏置时的 1.5 倍，负荷较小的一侧可低至 0.5 倍。**正常**（默认）会把振动发送到过弯时车辆*把你推向*的那一侧震动垫上（物理上是弯道外侧，你的身体被压向的那一侧）。**反转**会把这个方向调换过来。由于「哪一侧承受负荷」这个符号约定并非每款游戏都有文档说明，而是推断得出的，建议两种模式都试一下，选择与你实际过弯感受相符的那一个。

**整合车轮抱死与打滑。** 默认开启（让全新安装无需寻找开关即可体验该效果——这是相对早期默认关闭的一次刻意改动，详见 `docs/integrate-default-report.md`）。在未接入抱死/打滑信号时保持静默——下方公式在 `车轮数值` 为 0 时结果恒为 0，这正是尚未配置车轮抱死/打滑通道的玩家所看到的效果。取消勾选可恢复为改动前普通的 G 力体验。启用后，车轮抱死/打滑信号会使每一对左右震动垫产生叠加在当前 G 力水平之上的交替抖动——震动垫对的*振幅范围*会随着车轮当前抱死/打滑的程度增大，而其*中心值*始终锚定在原本的 G 力数值上，因此开启该功能不会造成任何跳变。具体公式（每对震动垫）：`振幅范围 = G力数值 × (车轮数值/100) × 缩放系数`，`半幅 = 振幅范围/2`，`输出（左/右） = 中心值 ± 半幅 × sin(2πft)`——如果得到的范围会超出 0-100，整个范围会被**平移**（而不是压缩），以保留其完整宽度；只有当范围本身宽于 100 时，才会退回到以 50 为中心、简单裁剪到 0-100 的处理方式。三个可配置项：**抖动频率**（1-20 赫兹，默认 **10 赫兹**——相比原先的 3 赫兹有所提高，车主本人在真实硬件上试用 3 赫兹后反馈 10 赫兹的手感明显更好；1-20 赫兹的上下限本身未变），以及各自独立的**车轮抱死缩放系数** / **车轮打滑缩放系数**（0-10，必须 ≥ 0，默认各为 **1.5**——相比原先的 1.0 有所提高，即原始（未缩放）振幅的 **150%**，同样基于希望默认抖动更明显的驾驶员反馈；输入框标签会显示「1.0 = 100%」，让这个乘数读起来更直观，同时避免额外增加一个会对同一振幅重复缩放、相互矛盾的「强度」控制项）。具体而言：当震动垫数值为 100、车轮数值为 60 时，*旧*默认值产生的抖动范围为 60（满分 100）；*新*默认值产生的抖动范围为 90。当抱死和打滑同时非零时，取两者缩放后数值中**较大**的一个来驱动抖动（而不是相加），这样两个通道短暂重叠时也不会让振幅翻倍。
> **请勿与第 5 层脉冲自身独立、未改变的下限混淆：** 上文的「达到最大值时脉冲振动」仍然强制执行其自身 200 毫秒（5 赫兹）的最小间隔——这是车轮抱死/车轮打滑标签页上的另一个设置，不受此处抖动频率改动的影响。

### 常规标签页

**启用诊断。** 默认关闭。开启后，上面列出的 9 个 `Diag.*` 属性也会被发布，并会记录额外的提示性日志——便于排查问题，或者用来构建一个仪表盘，实时显示某个通道*为什么*表现成现在这样。SimHub 仅在启动时注册一次属性，因此该选项需要**重启 SimHub** 才能生效——仅点击应用并不会让这些属性出现。

**将本次会话导出为 CSV。** 默认关闭。开启后，所有已发布的属性（包括产品属性和诊断属性）都会写入一个 CSV 文件，保存在与本插件设置文件相同的 SimHub `PluginsData\Common` 目录下，便于离线分析或基于真实录制数据进行调校。立即生效，无需重启。

### 持久化文件

两个文件，都位于 SimHub 的 `PluginsData\Common` 目录下（通过 SimHub 自身的 `PluginManager.GetCommonStoragePath` 解析得到，绝不硬编码路径）：

- **`QAdvanceFeedback.config.json`**——四个设置标签页上的全部内容。插件加载时读取一次，点击应用时保存（关闭 SimHub 时同样会保存）。如果仍存在旧文件名（`plugin.QAdvanceFeedback.config.json`，来自本插件的早期版本），会在新文件尚不存在的第一次启动时自动导入一次。
- **`QAdvanceFeedback.Parameters.json`**——每一个**已学习**的数值：车轮抱死/车轮打滑通道学习到的峰值 G 参考值，以及 G 力通道自动学习到的最大值，均按**游戏和车辆**分别存储，因此切换车辆（或游戏）时会自动加载该组合各自之前学习到的数值，而不是所有组合共用同一个数字。每个符合条件的帧都会实时更新内存中的缓存；后台定时器每 5 秒检查一次，只有在确实发生变化时才会写入磁盘，SimHub 关闭时还会额外执行一次同步的最终写入。文件损坏时会自动降级为「从零开始」，而不会导致插件崩溃。此文件由 `plugin.QAdvanceFeedback.runtime.json` 改名而来；如果仍存在旧文件名的文件，会被导入一次——由于旧文件产生于按游戏/车辆分别存储之前，其中的单一全局数值会作为每个通道升级后遇到的第一辆全新车辆的初始种子值，而不是被直接丢弃。

## 从源代码构建

```bash
bash tools/fetch-simhub-refs.sh 9.11.22          # 将参考程序集提取到 lib/ 目录
MSBuild QAdvanceFeedback.sln -t:Restore,Build -p:Configuration=Release
dotnet test QAdvanceFeedback.Tests/QAdvanceFeedback.Tests.csproj
```

`lib/` 目录故意没有提交到版本库（见 `.gitignore`）——其中的七个 DLL（`SimHub.Plugins`、`GameReaderCommon`、`MahApps.Metro`、`Newtonsoft.Json`、`SimHub.Logging`、`log4net`、`System.Windows.Interactivity`）是从官方 SimHub 安装包中提取出来的第三方二进制文件，本项目无权重新分发。`tools/fetch-simhub-refs.sh` 可以在一次全新的克隆上从零重建 `lib/` 目录，默认针对 **SimHub 9.11.22** 版本，运行时不需要预先安装任何东西——它会下载 SimHub 发行版压缩包和安装程序，使用 `innounp`（Inno Setup 6.4 自身的解包工具；更老版本的 `innounp`/`innoextract` 不支持该版本）解包安装程序，然后把七个 DLL 复制出来。

算法本体位于 `QAdvanceFeedback/Core/` 中，**完全不依赖 SimHub**——测试项目直接链接编译这些源文件，而不是引用编译好的 DLL，因此整个算法可以在一台完全没有安装 SimHub 的机器上进行测试；一旦有 SimHub 依赖悄悄混入 `Core/`，测试项目会立即无法编译。

### 仓库结构

遥测数据依次流经五层（遥测接口 → SimHub 适配器 → **Raw** → **Normalized** → **Projected**），
外加一个独立的 G 力子系统和一个设置/持久化层——各层各自发布什么参见上文"五层架构"一节。现在已经
没有 `Private/` 文件夹，也没有基于反射的工厂了：实现这些层的每一个文件都在本仓库中，分别位于
`QAdvanceFeedback/Core/`（第 1/3/4/5 层、G 力）和 `QAdvanceFeedback/`（第 2 层、设置界面、持久化）
之下。完整的分层职责与逐文件索引见 [`docs/architecture.md`](docs/architecture.md)。

**669 个测试，0 个编译警告，单 DLL 分发**（`bin\Release\net48\` 目录下只有 `QAdvanceFeedback.dll` 及其 `.pdb`——每一个 SimHub/GameReaderCommon/MahApps/Newtonsoft 引用都设置为 `<Private>false</Private>`）。现在已经没有单独的"干净克隆"版本需要构建或测试了——见上文"仓库结构"。

## 已知局限性 / 未经验证之处

按照本项目一贯的做法，坦率地列出：

- **本项目从未在真实的 SimHub 会话中运行过，也从未在真实游戏或真实震动硬件上运行过。** 669 个测试全部都是纯粹的、离线的、基于手工计算预期结果的单元测试（持久化层则使用真实的临时文件进行测试）——实际安装到 SimHub 中、读取真实游戏数据、驱动真实震动器时的运行表现尚未得到验证，在当前开发环境中也无法验证。
- **`LongitudinalG` 的符号约定以及 `LateralG` 的符号-方向对应关系都是推断得出的**，而非 SimHub 文档中明确说明的事实（已直接核实过——没有相关文档注释，也没有附带的 XML 说明）。方向（刹车还是加速）是根据车速的差分得出的，从不依赖 `LongitudinalG` 的符号，专门为了让这个不确定性不会影响车轮抱死/车轮打滑通道；G 力通道在选择震动垫时确实读取了符号，因此如果某款游戏的符号是反的，修正方法是一行代码的调换（见 `Core/GForce/GForceEngine.cs` 自身的注释）。
- **「Normalized」内部的逐轮再分配是一种启发式方法**（利用 Raw 自身的四轮比例，重新分配一个车辆级别的严重程度），而不是物理推导出的逐轮模型——本插件被明确禁止使用基于轮速推导出的打滑数据，因此这是在此限制下能获得的最佳逐轮信号，而不是声称比实际更精确。
- **G 力洗出模型的时间常数是根据离散滤波器递推公式的离线仿真校准得到的**，而不是基于真实硬件——它们在该仿真和引擎自身的单元测试中都产生了预期的定性效果，但在真实震动垫上实际的体感尚未得到验证。
